# 玩法设计流程（Game Design Workflow）

> 当制作人想设计新玩法、新系统、新机制（而不是加具体内容）时走这个流程。
> 玩法设计是"方向性"工作,决定游戏怎么玩、为什么好玩。

---

## 一、流程适用场景

- 设计核心玩法循环（局内/局外/长期）
- 设计新系统（如套装系统、天赋树、竞速排行榜）
- 设计副本机制（新的独特玩法）
- 重大玩法调整（如改战斗手感、改成长节奏）

**不适用**：加具体装备/怪物（走内容制作流程）；调数值（走数值平衡流程）。

---

## 二、标准流程（7 步）

```
制作人提出玩法想法
   ↓
1. 目标澄清（游戏策划）
   ↓
2. 玩法方案设计（游戏策划）→ 多个备选方案
   ↓
3. 系统拆解（系统设计师）→ 如何实现
   ↓
4. 制作人选方案 ← 决策点
   ↓
5. 原型验证（程序 快速实现可玩原型）
   ↓
6. 试玩反馈（制作人 + 测试）
   ↓
7. 迭代或确认 → 通过后进入内容制作/实现流程
```

---

## 三、各步骤详解

### 步骤 1：目标澄清（游戏策划）

**输入**：制作人玩法想法（如"我想加一个天赋树系统"）

**游戏策划要做**：
- 确认产品目标：这个玩法要解决什么问题？（增加深度？拉长游戏时长？差异化卖点？）
- 确认体验目标：玩家玩这个玩法时应该有什么感受？
- 确认范围：第一版做到什么程度？后续如何扩展？
- 确认约束：3个月能做吗？配置表驱动吗？

**输出**：明确的设计目标文档

**示例**：
```
目标：天赋树系统
- 产品目标：增加局外成长深度，让失败的局也有收获
- 体验目标：玩家感到"我在持续变强，下次能打得更远"
- 范围：第一版 3-5 条天赋线，每条 5-8 个节点，用金币解锁
- 约束：配置表驱动，DLC 能追加新天赋线
```

---

### 步骤 2：玩法方案设计（游戏策划）

**游戏策划要做**：
1. 读取 GDD.md,确认与核心玩法一致
2. 设计 2-3 个备选方案（不同侧重点）
3. 每个方案包含：
   - 核心玩法循环（玩家做什么 → 得到什么 → 为什么想再做）
   - 关键机制描述
   - MVP 版本范围（第一版最小可玩内容）
   - 风险与取舍
   - 后续扩展空间

**输出**：2-3 个备选方案文档

**示例备选方案**：
```
方案 A：线性天赋树
- 3 条独立线（攻击/防御/技能），玩家自由点
- 优点：简单清楚，配置表友好
- 缺点：深度有限
- MVP：3 条线各 5 节点

方案 B：网状天赋图谱
- 类《流放之路》网状，自由路径
- 优点：深度极高，可玩性强
- 缺点：复杂，可能超 3 个月范围
- MVP：缩减版，30 个节点互联

方案 C：不做天赋树，改强化装备槽位
- 用金币解锁/升级装备槽，直接增强装备效果
- 优点：简单，和核心"装备构筑"直接挂钩
- 缺点：缺乏天赋树的"规划感"
```

---

### 步骤 3：系统拆解（系统设计师）

**系统设计师要做**：
1. 读取游戏策划的方案
2. 拆解成可实现的模块：
   - 需要哪些配置表字段
   - 需要哪些代码逻辑
   - 与现有系统（装备/技能/成长）如何交互
3. 评估技术可行性和工作量
4. 标注哪些部分配置表驱动、哪些需要硬编码
5. 给出"配置表优先"的实现建议

**输出**：系统设计文档（技术视角）

**示例**：
```
方案 A 系统拆解：
- 配置表：talents.json（节点 id、效果、前置、成本）
- 代码模块：天赋树 UI、解锁逻辑、效果应用层
- 交互：天赋效果叠加到 base_stats
- 可行性：高，预计 2 周实现
- 扩展性：DLC 追加新线只需填 talents.json
```

---

### 步骤 4：制作人选方案 ← 关键决策点

**制作人要做**：
- 看懂各方案的产品收益和代价
- 选择最符合"暗黑奇幻 + 装备构筑深度"定位的方案
- 确认第一版范围（不追求完美，能玩就行）
- 批准进入原型阶段

**可能的决策**：
- 选方案 A，进入步骤 5
- 要求合并方案 A+C 的优点，游戏策划重新设计
- 推迟该玩法，优先做别的

---

### 步骤 5：原型验证（程序）

**程序要做**：
1. 快速实现最小可玩原型（MVP）
2. 不追求完美，能跑、能体验核心循环即可
3. 可以用占位美术、硬编码数据（后续再配置化）
4. 输出可运行的测试版本

**目标**：让制作人和测试能实际玩到这个玩法

---

### 步骤 6：试玩反馈（制作人 + 测试）

**制作人要做**：
- 实际玩原型
- 回答核心问题：
  - 这个玩法有趣吗？
  - 它给游戏带来的体验是我想要的吗？
  - 它和"装备构筑深度"卖点契合吗？
  - 我愿意为它投入后续开发时间吗？

**测试要做**：
- 试玩并记录体验
- 反馈：哪里爽、哪里卡、哪里不清楚
- 提出改进建议

**输出**：试玩反馈报告

---

### 步骤 7：迭代或确认

**三种结果**：

**A. 通过，进入正式开发**：
- 游戏策划写入 GDD.md
- 系统设计师设计配置表结构
- 进入内容制作流程（填配置表）+ 实现流程（完善代码）

**B. 需要调整，回到步骤 2**：
- 制作人指出哪里需要改
- 游戏策划调整方案，重新走流程

**C. 否决，该玩法暂时不做**：
- 原型代码归档或删除
- 记录否决原因到 decisions.md
- 优先级排到其他任务后面

## 四、派发 prompt 模板

```
【游戏策划】
制作人想法："{制作人原话}"

启动加载：
1. constitution.md
2. roles/game-designer.md
3. project/GDD.md
4. project/manifest.md

任务：
- 澄清设计目标（产品目标、体验目标、范围、约束）
- 设计 2-3 个备选方案
- 每个方案包含：核心循环、MVP 范围、风险取舍、扩展空间

交付：方案文档，供制作人选择
```

---

## 五、成功标准

一个玩法设计任务的成功标准：
- [ ] 设计目标明确（为什么做、做什么、做到什么程度）
- [ ] 备选方案清晰，优缺点透明
- [ ] 系统设计师确认技术可行
- [ ] 制作人选定方案
- [ ] 原型可玩，核心循环能体验
- [ ] 制作人试玩后确认"有趣、值得做"
- [ ] 与核心卖点"装备构筑深度"契合
- [ ] 第一版范围在 3 个月内可完成
