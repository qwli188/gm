# 代码实现流程（Implementation Workflow）

> 当系统设计和配置表已确定,需要程序实现代码逻辑时走这个流程。
> 程序主导,目标是"配置表驱动 + 可扩展 + 能运行"。

---

## 一、流程适用场景

- 实现新系统（装备、技能、副本系统等）
- 实现新的 effect kind（新词缀效果、新技能类型）
- 修复代码 Bug
- 性能优化

**前置条件**：系统设计已完成、配置表结构已定义。

---

## 二、标准流程（5 步）

```
收到实现任务（来自玩法设计/内容制作流程）
   ↓
1. 需求理解（程序）→ 读设计文档和配置表规范
   ↓
2. 技术设计（程序）→ 架构和模块拆解
   ↓
3. 代码实现（程序）→ 写 GDScript + 场景
   ↓
4. 自测（程序）→ 确保能运行
   ↓
5. 交付测试（测试）→ 通过 or 修 Bug 回步骤 3
```

---

## 三、各步骤详解

### 步骤 1：需求理解

**程序要读取**：
- 系统设计文档（来自系统设计师）
- 配置表规范（specs/*.tmpl.md）
- 现有代码结构（src/scripts/）
- GDD.md（理解游戏整体）

**程序要确认**：
- 配置表字段清楚了吗？
- 需要实现哪些逻辑？
- 与现有系统如何交互？
- 有没有可复用的代码？

---

### 步骤 2：技术设计

**程序要做**：
- 拆解模块（如装备系统 = 加载器 + 穿戴逻辑 + 属性应用层）
- 确定文件结构（哪些脚本、哪些场景）
- 设计配置加载流程（读 JSON → 校验 → 构建对象）
- 标注哪些地方用对象池、哪些地方需要优化

**输出**：技术设计简要文档（可以是注释或伪代码）

---

### 步骤 3：代码实现

**程序要遵守**：
- 配置表驱动：内容从 JSON 读,不写死
- 单一职责：每个脚本做一件事
- 错误显性化：配置错误要报错,不静默失败
- 注释关键逻辑：让 AI 后续能维护

**示例结构**：
```gdscript
# src/scripts/equipment_system.gd
class_name EquipmentSystem

var _equipment_data: Dictionary  # 从 config/equipment.json 加载

func load_equipment_config(path: String):
    # 加载、校验、报错

func equip_item(player, item_id: String):
    # 穿戴逻辑、属性应用

func apply_affixes(player, affixes: Array):
    # 词缀效果应用
```

---

### 步骤 4：自测

**程序要做**：
- Godot 项目能运行
- 配置能正确加载
- 核心功能跑通（至少手动测一遍）
- 没有明显报错

**不通过不交付测试。**

---

### 步骤 5：交付测试

测试按测试流程验证,发现 Bug 报告给程序,程序修复后重测。

---

## 四、代码规范要点

- 文件命名：snake_case（equipment_system.gd）
- 类命名：PascalCase（EquipmentSystem）
- 配置路径统一：res://project/config/
- 报错信息明确：push_error("装备 id '%s' 不存在" % item_id)
- 性能关键点：对象池、避免每帧遍历大数组

---

## 五、成功标准

- [ ] 代码符合配置表驱动原则
- [ ] Godot 项目能运行
- [ ] 配置能加载且错误能报出
- [ ] 核心功能实现
- [ ] 自测通过
- [ ] 代码有基本注释
- [ ] 测试验证通过
